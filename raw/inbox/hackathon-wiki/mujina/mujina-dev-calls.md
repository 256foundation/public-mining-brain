## Overview

The Mujina dev calls are public video calls where contributors to [Mujina](mujina-firmware.md) coordinate. Ryan announces each one on the 256 Foundation forum, and anyone may join. Eleven calls were announced between May and September 2026. The forum holds full recaps only for the first two calls. From call #3 on, the agenda, summary and transcript live in GitHub Discussions, so the forum threads are short pointers. This article records what the forum threads say about each call.

## How the calls run

- All calls use the same Jitsi room, `https://meet.jit.si/mujina-dev-call`.
- Every announcement is marked public. From call #3 the wording is "Public call, all are welcome."
- After the first call Ryan proposed running it again in two weeks, saying that "may or may not be the right cadence".
- Call #2 adopted a fixed order: walk GitHub discussions first, then issues, then PRs. It also capped calls at 1h30.
- From call #3 the announcements list a one-hour slot, 12:00 to 13:00 America/Chicago.
- Records moved off the forum at call #3 "because we prefer developer discussions go in GitHub Discussions". The mujina.org community page says records and agendas are posted in the Dev Calls discussion category, so people can catch up without attending.

## Call #1 (2026-05-04)

Ryan posted a recap on 2026-05-06.

- **Attendance:** 12+ people, a mix of devs, builders, students, pools, industrial miners and hardware vendors.
- **Vision:** be the Linux kernel project of Bitcoin mining. Open source and developed in the open, built by volunteers and industry together, with hardware support for all chips, hashboards and control boards. It should serve industrial operators, heat co-producers and home miners alike.
- **State:** the core is in place. The work now is hardware breadth and features.
- **Current priority:** official S19 support, to enable early adoption.
- **In progress across the community:** LibreBoard control board support, EmberOne00 v6 hashboard support, S19 support (hashboards, stock control boards and an easy installer), an SV2 client, a BZM2 chip driver, Bitaxe Bonanza board support, and YAML config files.
- **Contribution flow and communication channels:** see [Contributing and Mujina Improvement Proposals](contributing-and-mips.md).

## Call #2 (2026-05-18)

The summary was generated by AI from the meeting recording and posted by Ryan. Attendees were Ryan (host), Johnny9, Gary, Jayr, Skot, Tyler and David.

### Config file and persistence

The topic came from Jeff's open YAML config PR. Ryan said it needed a design conversation before more code landed.

- Most changes made through the API should survive a restart. Johnny9 put it as "config, by definition, is something you persist". Skot's example: derated settings after an overheat must survive a power cycle.
- Two layers were proposed. A user-managed config is hand-edited and never clobbered by the daemon. A process-managed config is machine-readable and freely rewritten by the daemon.
- The schema must tell defaults from user overrides, so updates can move defaults without trampling user values.
- Hardware config (boards, I2C devices, fans) and application config (pools, API, log levels) feel like different things.
- Discover hardware dynamically where possible. Use static config only for what cannot be discovered, such as fan presence, I2C addresses and power-supply wiring.
- Jayr wants a way to override config for one specific device without touching driver defaults.
- Open question: when the user passes a config file on the command line, where do API-driven changes get saved? Gary floated an explicit export command.

Ryan's follow-up to this became MIP-0001. See [Contributing and Mujina Improvement Proposals](contributing-and-mips.md).

### Hardware-in-the-loop testing and safety

- Ryan wants integration tests on real hardware soon.
- Self-hosted runners are awkward for an open project. Random PRs should not be able to flash firmware onto someone's house hardware.
- Johnny9 suggested starting with a GitHub workflow gated on maintainer approval.
- The direction settled on is a standardized downloadable test suite that anyone with hardware can run and publish results from. A central orchestrator is deferred.
- Skot cautioned against an official Mujina lab carrying central responsibility for safety across all devices.
- Bitaxes are the safe starter target: "better to melt one of those" than a 3kW S21.
- Jayr suggested a ProtonDB-style community site for hardware compatibility reports.

### Community ports

The call discussed porting Mujina to other miners with AI agents. See [Porting Mujina to Other Miners](porting-mujina-to-other-miners.md).

### Bitaxe Bonanza USB identification

Johnny9 needed to tell a Bitaxe from a Bitaxe Bonanza over USB. The decision was to change the USB product string to encode the hardware version (for example "Bitaxe 1002") for Bonanza, then iterate. The Bitaxe naming inside Mujina assumes Gamma and needs to get more specific.

### Adjacent news

David's company released its internal firmware orchestration and miner-management app as open source. They plan to add native Mujina support, reading hash rate, uptime and temperatures through the Mujina API.
